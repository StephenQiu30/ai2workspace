## 协作目标

将“解决什么问题、依据什么设计、如何证明完成”保存在同一知识库。人和 AI 读取同一份资料，通过文档链接、条目 ID 和实际工程路径协作。

本规范适用于 `ai2workspace`。协作流程涵盖需求确认、产品定义、设计、实现、验收和交接；各阶段引用同一项目资料，记录真实决定与交付证据。

## 文档链路与职责

| 文档 | 需要回答的问题 | 权威内容 | 模板 |
| --- | --- | --- | --- |
| Requirement 需求记录 | 谁在什么场景遇到什么问题？需要什么功能与质量？ | 原文、来源、功能需求、非功能需求、外部约束与确认记录 | [需求模板](./templates/001-需求记录模板.md) |
| Design 设计文档 | 如何组织产品体验与工程职责？为什么选择这个方案？ | 方案、职责、交互、接口、数据、取舍与风险 | [设计模板](./templates/002-设计文档模板.md) |
| PRD 产品文档 | 本次产品交付什么？怎样判断符合需求？ | 根据需求与设计收敛范围、业务规则与产品验收 | [PRD 模板](./templates/003-PRD模板.md) |
| Plan 执行计划 | 分几步交付？依赖什么？如何验证和交接？ | 任务拆分、执行状态、实际证据与剩余事项 | [计划模板](./templates/004-执行计划模板.md) |
| Research 调研资料 | 有什么依据？观察到什么？哪些结论仍需验证？ | 来源、调研记录、术语及被引用的结论 | [调研模板](./templates/005-调研记录模板.md) |

主链路固定按 **Requirement → Design → PRD → Plan** 展示：先保存需求与确认，再形成方案，用 PRD 收敛产品规则与验收，最后拆解执行。设计可以先引用需求；PRD 创建或变更后再补齐 FR / AC 映射，不能因为 PRD 尚未编写就伪造产品条目。各阶段可以迭代回访；每份文档的编号用于分类内定位，不代表评审、实现或发布已完成。

Research 是贯穿各阶段的依据，不是执行计划之后才能进行的步骤。调研记录、术语和参考资料放入同一资料分类，通过链接支持对应需求、设计、PRD 或计划。小改动只更新受影响的资料，不为凑齐链路创建空文档。

产品范围以已确认需求和 PRD 为依据。设计建议不能自动变成需求；技术限制影响产品行为时，记录影响并取得对应决定。执行计划引用定义，不另写一份产品规则。

### 需求、设计与验收的生命周期

每个可独立评审和验收的专题维护一条文档链。需求记录先明确使用者、场景、原始来源、业务范围及约束；功能条目写明需要达成的行为及异常，非功能条目写明适用场景、质量要求和可验证结果。按专题风险选择安全与隐私、可靠性与恢复、性能与资源、可访问性、兼容性、可维护性和可观测性。缺少基线的数值记录测量口径、确认时点及影响。质量模型与需求追溯参考 [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html) 和 [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html)。

| 阶段 | 进入下一阶段前需要明确的内容 |
| --- | --- |
| 需求定义 | 来源、首版范围、角色、`R` 功能需求、`NFR` 质量需求、外部依赖与待决项 |
| 系统与详细设计 | 系统边界、职责、页面、数据权威、接口、状态、依赖、失效恢复、适用权限与风险；共享约束由总览引用 |
| PRD 与评审 | `FR` 对应功能需求，`AC` 覆盖功能与非功能需求；明确测试条件、操作与预期。按对实施或发布的影响关闭阻塞项 |
| 实施与验证 | 获授权后由执行计划串起规格版本、测试任务和证据；区分模拟、集成与真实依赖验收 |
| 发布、运行与演进 | 按验收证据决定发布；记录版本、兼容与恢复、监控及运营交接；修改范围时更新上下游引用 |

历史方案在文档开头标明适用功能、记录时点与现行入口。保留当时的需求、约束和执行证据。实施前按现行专题及授权确认任务，并用当前代码、配置和可复核的证据确定实现状态。

## 目录与唯一来源

系统拓扑、跨域职责、共享技术选型和架构图统一维护在 [workspace/ARCHITECTURE.md](../ARCHITECTURE.md)。专题正文位于 `workspace/content/`，从[文档导航](./00-文档导航.md)及各分类的 `00` 导航进入。专题设计引用总体架构，并记录本专题的接口、流程和验收。模板集中在 [templates](./templates/00-模板导航.md)。

根目录 `PROJECT.md` 保留为当前仓库的工程结构、服务边界与选型入口，根目录 `DESIGN.md` 指向[学屿品牌与界面设计规范](./design/010-学屿品牌与界面设计规范.md)。本规范定义通用协作与工程约定，界面视觉令牌和页面模板在 `DESIGN.md` 对应的知识正文中维护。业务专题材料放在下述知识目录，模块 README 说明实际启动与检查，生成文件归各工程的构建流程管理。

PRD 和实施计划的方法优先复用已启用的插件：`pm-execution:create-prd` 负责 PRD 创建与评审，`superpowers:writing-plans` 负责实现计划拆解。本地模板保存项目字段和引用约定，项目 Skill 负责读取上游与落盘适配，不在仓库维护插件方法的副本。

```text
workspace/content/
├── 00-文档导航.md
├── 01-项目文档与设计规范.md
├── requirement/00-需求导航.md
├── design/00-设计导航.md
├── prd/00-PRD导航.md
├── plan/00-Plan导航.md
├── research/00-调研导航.md
└── templates/00-模板导航.md
```

各分类的 `00` 页面用来定位关键资料，正文和模板沿用三位编号与中文文件名，如 `NNN-中文设计主题.md`。对应页面标题为 `NNN · 文档标题`。文件名保留必要的 Agent、PRD 等术语，使用无空格写法。

序号在每个分类中独立分配：新增前先检查该分类已用的最大编号并递增，不填补删除造成的空号，不因插入、改名或调整展示顺序重新编号已有文档。不同阶段的相同序号不自动表示同一需求；跨阶段通过专题名称、文档 ID 和实际链接关联。迁移保留原有文档 ID、R / D / FR / AC / T-ID、确认记录与历史证据。

`meta.json` 用于分类标题及首页顺序。Fumadocs 按文件名发现和排列分类内的页面，`00` 导航只列常用入口。

每篇文档保留一份正文，跨阶段通过实际文件的相对链接关联。例如需求关联已有的 `./design/001-学习社区与通用Agent顶层设计.md`；尚未创建的资料写“未创建”，不预造链接。复制模板后替换 frontmatter、移除模板使用说明，按实际位置重算相对链接；模板参考不能冒充业务依据。业务源码保存在实际工程，知识文档只引用工程位置、版本和适用决定，不新增工程登记系统。

## 来源、标识与状态

需求来源写明用户原话、消息或材料的引用位置，以及已知的日期和确认结论。来源缺失时标记“待补充”，不把截图里的示例、AI 建议或推断记为用户已确认内容。

| 内容 | 标识示例 | 用法 |
| --- | --- | --- |
| 文档 | `REQ-项目-主题`、`DES-项目-主题`、`PRD-项目-主题`、`PLAN-项目-主题`、`RES-项目-主题` | 项目内唯一，移动文件后保持原标识 |
| 需求条目 | `R-01`、`NFR-01` | 分别用于功能需求与质量需求，在需求文档内稳定编号；保留原有编号 |
| 产品行为与验收 | `FR-01`、`AC-01` | PRD 引用 `R` 或 `NFR`，验收描述可观察结果 |
| 设计决定 | `D-01` | 说明取舍、依据和受影响的产品条目 |
| 执行任务 | `T-01` | 引用设计与验收，记录执行和证据 |

短 ID 与文档 ID 一起引用，不能只用 `AC-01` 指代不同文档的验收。相对链接定位到实际文件或已存在的标题；空白占位使用“待填写”，不创建无效链接。

需求、PRD 和设计使用“草稿、待确认、已确认、已替代”等定义状态，确认人和结论未知时保持待确认。计划按每项任务记录“未开始、进行中、阻塞、已完成”。文档评审、代码实现、验收和上线是不同事实，分别记录。

## 分工与协作

| 责任 | 主要参与者 | 交付内容 |
| --- | --- | --- |
| 目标、需求与范围 | 业务负责人、PM | 原意、优先级、范围取舍及确认 |
| 方案与工程职责 | RD、前后端研发 | 模块边界、接口、数据与技术取舍 |
| 交互与视觉 | UIUE、前端研发 | 流程、状态、组件与设计依据 |
| 验收与质量 | QA、产品及研发 | 可观察条件、实际结果和缺陷 |
| 发布与运行 | OP、研发 | 环境、配置、上线步骤及恢复方案 |
| 计划与交接 | POM、各任务责任人 | 依赖、进度、阻塞、证据与下一步 |

这是文档责任说明，不是目录权限表或自动角色调度。一个人可以承担多个责任，具体参与者按实际任务填写，未知姓名、日期和承诺不补造。

## 项目设计要求

设计前读取现有需求、调研、代码和适用工程规范；PRD 已存在时同时读取并核对其产品约束。描述实际现状、已确认目标、设计建议与待定问题，明确本次范围。

- **职责与复用**：按业务职责划分模块，优先现有组件和框架能力；新增抽象要说明具体复用需求或边界收益，避免单一用途包装。
- **交互与状态**：说明主要流程、输入、正常结果，以及适用的空、加载、失败、权限和恢复状态；注明设计稿或界面基线来源。
- **接口与数据**：需要时列出输入输出、字段约束、权限、错误和一致性要求；涉及现有数据变化时单独说明兼容与恢复安排。
- **方案取舍**：比较影响决策的可行方案，记录选择依据、成本、风险和待验证假设，不要求为简单修改虚构备选方案。
- **质量目标**：性能、容量、可用性和成本有业务要求或实测依据时写具体条件；没有依据的数值保持待确认。
- **交付边界**：列出实现顺序、验证方法及必要的发布条件；文件已写、构建通过或评审通过不能代替产品验收。

## 工程规范与目录设计

本仓库 Go 业务服务以 [Google Go Style Guide](https://google.github.io/styleguide/go/guide) 为规范基线，[Style Decisions](https://google.github.io/styleguide/go/decisions)补充具体决定，[Best Practices](https://google.github.io/styleguide/go/best-practices)作为设计参考；以[官方概述](https://google.github.io/styleguide/go/)说明的优先级处理差异。前端以 [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html) 为基线，保持 strict。代码规范、服务边界与框架约定分别记录。

### 单体设计与 API 自动生成

- Go 后端在 `backend/` 维护一个 Go module、一个 HTTP 入口、一份 Swagger 和一个部署产物。
- PostgreSQL 表与索引在 `backend/schema.sql` 定义。开发环境以空库初始化，应用从统一连接池访问数据。业务约束由所属模块实现。
- API 契约的唯一来源是业务 Handler 的 Swaggo 注解和 Go DTO 标签。通过后端 Makefile 生成 `backend/api/` 中的 Swagger，再用 `openapi2ts` 从该产物生成前端类型和调用函数。禁止手动修改生成文件。
- 副作用导入放在程序入口或确有需要的测试中。
- 可能失败的操作返回 `error`，跨边界返回时补充操作上下文。请求和初始化使用可取消的 context，后台协程由启动方负责收尾。手写 Go 文件用 `gofmt`，静态检查与竞态测试通过后端 `make check` 执行。

### 单体模块的目录与依赖

以 [Go 官方服务端项目布局](https://go.dev/doc/modules/layout#server-project)为基础，在 `backend/internal/` 按业务域组织代码。包名使用简洁的小写名称。

| 位置 | 职责 |
| --- | --- |
| `cmd/ai2workspace/` | 读取配置、创建连接池、启动 HTTP 和处理退出信号 |
| `internal/app/` | 装配各业务模块，注册公共路由，挂载各模块路由 |
| `internal/infra/` | 进程配置、共享 PostgreSQL 连接等基础设施 |
| `internal/<业务域>/module.go` | 创建并组装模块，通过 `RegisterRoutes` 挂载 HTTP 路由，对其他模块提供业务能力 |
| `internal/<业务域>/adapter/` | HTTP 路由、处理和 DTO，PostgreSQL 持久化，外部 API 与邮件等具体实现 |
| `internal/<业务域>/application/` | 用例、任务执行、业务流程编排及所需的接口 |
| `internal/<业务域>/domain/` | 业务实体、值、状态和规则 |

- 依赖方向为 `adapter → application → domain`。适配层可以使用本域的领域类型。领域层只依赖本域的领域包和适用的基础库。应用层定义并使用用例需要的接口，模块根包注入具体实现。
- 各层先按实际职责组织文件，再按业务需要拆功能包。Agent 运行属于 `agent/application/agent`，知识索引属于 `agent/application/knowledge`，模型调用适配属于 `agent/adapter/provider`。有实际功能时创建相应目录。
- 生产代码跨域调用通过对方根包或注入的 Go 函数和接口。框架和业务存储实现随各域适配层维护。
- 每个业务域负责自己数据的读写规则。跨域需要购买权益、课程交付状态、身份或通知时，由相应模块提供业务能力。
- 测试放在 `backend/tests/<业务域>/`，可导入被测域的功能包。全应用验收与依赖方向检查放在 `backend/tests/app/`。

### 前端规范（Vercel 最佳实践与 Google TS 规范）

前端业务工程严格遵守 **Google TypeScript Style Guide** 与 **Vercel React / Web Interface Guidelines** 最佳实践：

#### 1. Google TypeScript 代码规范
- **类型严格性**：保持 `strict: true`，严禁使用 `any`，外部输入与未知结构必须使用 `unknown` 并通过类型守卫（Type Guard）或模式匹配收窄；禁止使用无依据的强制类型断言（`as SomeType`）。
- **命名约定**：手写源码文件统一采用 `snake_case.ts/tsx`；类型、接口与 React 组件采用 `UpperCamelCase`；函数、方法与变量采用 `lowerCamelCase`；常量采用 `SCREAMING_SNAKE_CASE` 或 `lowerCamelCase`。
- **导出与类型导入**：优先使用命名导出（Named Exports），仅在 Next.js 页面与布局路由入口保留框架要求的默认导出；导入类型时严格使用 `import type`，明确值与类型的引用边界。
- **数据结构声明**：对象数据结构统一优先使用 `interface`，联合类型、交叉类型或复杂类型表达式使用 `type`。

#### 2. Vercel React / Next.js 性能与工程规范
- **服务端组件优先（RSC First）**：页面默认为服务端组件（Server Components），将数据获取与初始渲染保留在服务端；交互逻辑精准下沉到 `'use client'` 树枝叶子组件，最大限度减少客户端 JavaScript 打包体积。
- **服务端请求与上下文隔离**：服务端 API 客户端请求选项必须按每次调用上下文独立构建（如 `getServerRequestOptions()`），严禁在全局或跨请求共享用户 Token / Cookie；内部后端地址与敏感配置严禁泄露至浏览器端。
- **消除请求瀑布流（Waterfall Elimination）**：合理利用 React Suspense 边界与流式渲染（Streaming），避免组件层层嵌套等待引起的页面级瀑布流阻塞。
- **错误边界与交互韧性**：关键功能区域使用 Error Boundary 封装，当接口故障或后端离线时，页面展示明确、可恢复的重试交互（如“重新检查”），绝不白屏且严禁向用户暴露内部堆栈。

#### 3. Vercel Web Interface Guidelines 界面与可访问性规范
- **全键盘与焦点可访问（a11y）**：所有交互控件（按钮、链接、输入框、下拉菜单）支持标准键盘导航（Tab/Shift+Tab 切换焦点，Enter/Space 触发，Esc 退出弹窗）；焦点状态必须具备清晰高亮（Focus Ring / Focus Visible）。
- **布局与视口适应**：验证桌面、平板和移动视口及窄屏重排，确保页面无意外横向滚动。移动端触控目标至少 44 × 44 CSS px。尺寸与布局规则见[学屿品牌与界面设计规范](./design/010-学屿品牌与界面设计规范.md#组件与验收)。
- **状态感知设计**：耗时操作提供明确的加载状态（Loading Skeleton / Spinner），操作按钮在请求中禁用以防止重复提交。每个支持的主题均验证颜色、对比度与交互状态，达到 WCAG AA；主题范围以[视觉基础](./design/010-学屿品牌与界面设计规范.md#视觉基础)为准。

#### 4. 视觉基线与页面设计

`frontend/` 的业务界面采用[学屿品牌与界面设计规范](./design/010-学屿品牌与界面设计规范.md)。视觉与交互以 Vercel Geist 和 Web Interface Guidelines 为参考，设计与评审用 UI/UX Pro Max 检查布局、可读性和可访问性，实现复用 shadcn/ui Radix Nova 及共享语义令牌。营销页参照 [Landing Page 模板](./design/010-学屿品牌与界面设计规范.md#landing-page-模板)。`workspace/` 的界面沿用 Fumadocs Spacious。

### 框架与生成代码例外

新增例外在实际设计中说明文件范围、具体冲突、原因和验证方式，避免扩展到整个工程。Swagger、生成客户端和运行时解析规则的唯一来源保持一致：手工维护 Go DTO、标签与必要注释，通过工具生成文档及客户端；生成文件不进入公开知识源。完整生成流程和目录归属见根 `PROJECT.md`，本页不复制服务配置。

### 检查与验收边界

| 对象 | 采用方式 | 检查边界 |
| --- | --- | --- |
| Go 服务 | 格式、静态检查、测试、独立构建及设计复核 | 单体统一检查依赖、包职责、错误与并发；有并发行为时运行适用的竞态检查 |
| TypeScript 前端 | 类型、ESLint、Prettier、生产构建及设计复核 | 覆盖手写代码与例外边界；生成目录必须可重建且能被消费者正确使用 |
| Swagger / 客户端 | 文档生成、路由覆盖、生成类型及实际接口调用 | 自动生成不替代真实输入输出、权限与错误路径的验证 |
| 知识库 Next.js / Fumadocs | 官方布局、组件、主题变量和内容源 | 文档通过内容文件生成，不手写逐页映射；现有工程按实际适用检查执行 |
| 界面与可访问性 | [Vercel Web Interface Guidelines](https://vercel.com/design/guidelines)、[学屿组件与验收](./design/010-学屿品牌与界面设计规范.md#组件与验收) | 验证键盘、焦点、主题及响应式；知识库沿用 Spacious，业务前端使用 shadcn / Radix Nova |

尚未初始化的业务服务只能记录检查要求，不能记为通过。其他外部工程按其实际技术栈确定适用约束，不直接套用本仓库的目录或部署选型。

## 验收、变更与交接

PRD 为关键行为定义可观察的验收条件。计划为每项验收安排验证任务；设计在必要时补充技术验证条件。要求、方案或范围变化后，记录变更原因、决定来源和受影响的文档与任务，并更新链接，保留已发生的事实。

完成记录至少包含实际执行内容、环境或版本、命令或操作、观察结果和证据位置。测试未执行、失败、跳过、模拟和真实验收分别注明；阻塞写出原因与下一步。发布状态只引用实际发布结果。

日志、凭据、本机绑定及私有运行记录不进入公开正文或 Skill。公开证据只保留必要摘要和可分享引用。

## Skills 与插件协作

项目级 Skills 位于仓库根目录 `.agents/skills/`。在该项目中按工作目标选择：

| 项目入口 | 方法来源 | 项目补充职责 |
| --- | --- | --- |
| `$workspace-requirements` | 需求来源与确认规范 | 保存原意、确认与需求标识 |
| `$workspace-design` | 实际工程与适用设计规范 | 关联需求、调研、职责、技术决定和验证 |
| `$workspace-prd` | `pm-execution:create-prd` | 依据需求与设计收敛 PRD，保留 FR / AC 关联 |
| `$workspace-plan` | `superpowers:writing-plans` | 适配计划路径，关联验收、执行证据与交接 |

### PRD 方法

创建或评审 PRD 时实际读取 `pm-execution:create-prd`，默认生成精简、可用于首版决策的文档，按用户要求再展开。上游保留目标用户与价值主张，项目补充需求来源和可观察的产品验收；两者收敛在同一份 PRD。

问题、目标用户或成功判据仍不清楚时，按上游要求先集中澄清，不能以模板中的“待填写”替代回答。用户明确允许带假设继续时，才将缺口标为假设后成稿。成稿不保留未知联系人等无必要占位。

### 计划拆解方法

多步实现计划实际读取 `superpowers:writing-plans`，围绕具体文件职责、接口、独立可验证交付和检查步骤拆分，采用其当前要求的计划头与自检。项目补充稳定 ID、验收映射、实际状态和交接；仅更新进度不必重新拆解整份计划。

本项目计划位置为 `workspace/content/plan/NNN-中文文档名称.md`，明确替代上游默认的 `docs/superpowers/plans/`；PRD 位于 `workspace/content/prd/NNN-中文文档名称.md`，需求和设计分别位于 `requirement/`、`design/`。各分类分别分配文档序号，跨阶段通过专题、稳定 ID 和实际链接关联。用户明确指定的输出位置优先，既有文档更新同一份正文，不创建平行副本。

### 可用性与交付边界

调用时提供专题、已有资料和输出位置。项目 Skill 从宿主当前可用技能中发现并读取对应插件，不绑定某台机器的安装路径或缓存版本。插件缺失或无法加载时说明具体缺口，只整理已知依据，不宣称已按插件完成文档；记录实际使用过的方法来源，不把写入 Skill 名字当作已经调用。

插件的澄清、计划审阅与执行交接要求在适用任务中保留；项目模板不能绕过这些步骤。执行方式已有用户选择时继续沿用，未确认时不擅自派发子代理或启动实施。计划中的 Commit、推送或发布条目不授予执行权限，仍以用户当前授权及根协作入口为准。
