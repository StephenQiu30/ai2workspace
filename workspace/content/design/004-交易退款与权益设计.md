## 1. 背景、范围与规则来源

当前没有订单、真实支付、退款或权益实现。首版面向中国大陆／人民币，按课程一次性购买、平台统一收款，支持免费课及试看。管理员／受邀讲师供课不代表已支持讲师自动分账。

commerce 是售价、订单、支付尝试与到账事实、退款单和购买授予的唯一权威。课程版本、可售状态及可交付状态来自 learning；账号来自 identity；通知由 community 接收，不能成为支付完成的前提。

本设计采用用户接受的 [PRD 退款规则](../prd/004-交易退款与权益产品需求.md#退款规则)作为唯一商业参数来源，不重复维护天数、处理时限与金额规则。按观看／AI 使用扣费、部分退款、钱包、充值、订阅、套餐、优惠和自动分账均不纳入首版。

接受产品政策不代表已发生支出、商户开户、真实付款或生产发布。渠道能力、商户资质和实际退款流程仍需实施前核验；法律依据与产品政策分开记录，本设计不作新增法律结论。

## 2. 职责、目录与前后端边界

| 模块 | 计划路径与职责 | 依赖边界 |
| --- | --- | --- |
| 交易服务 | `backend/services/commerce/` 独立 Go module、数据库及账号 | 与其他域通过 HTTP 协作，不共享订单表或跨库事务 |
| 订单／定价 | `internal/orders/` 维护售价、购买快照、幂等下单和本人购买记录 | learning 提供可售快照与维护资格；客户端价格仅作展示 |

| 退款 | `internal/refunds/` 维护申请、审核、渠道尝试及人工异常队列 | 仅受授权后台可审核与重试；不由 Agent 执行 |
| 权益 | `internal/entitlements/` 维护与购买记录关联的授予、撤销及查询 | 不拥有媒体状态；当前课程可访问仍由 learning 综合判断 |
| 前端 | `frontend/src/features/commerce/` 及实际 `src/app/` 页面 | 课程购买、待确认、订单详情、退款申请／进度和运营审核 |

HTTP Handler、请求与响应 DTO 随所属业务包维护，入口只组装配置与依赖。共享前端生成配置、网关与部署文件由总计划集成负责人合并，不在本域添加编排脚本或手写 Swagger。

## 3. 购买、退款与用户状态

### 购买与确认

1. 前端展示课程公开内容、commerce 售价和购买政策；账号验证及当前课程可售条件通过后才创建订单。
2. commerce 查询 learning 的课程快照，读取本域权威售价，保存标题、课程版本、金额、币种及政策版本；有效购买权益存在时阻止重复购买。
3. 支付尝试使用稳定业务编号请求渠道；前端跳回只查询订单，不能凭 URL、浏览器事件或客户端“成功”授予权益。
4. 回调和主动查询经过相同校验及归一化流程；核对渠道签名、商户、订单、币种、金额、交易号后，记录到账事实。
5. 在 commerce 本地事务中确认到账、关联合法购买并授予该笔权益，记录待投递通知；外部通知失败不撤销付款或阻止本地授予。

下单请求重放返回同一订单；同一幂等键对应不同课程或输入返回冲突。后端阻止同一账号／课程在并发检查下重复建立有效购买，不能只靠页面禁用按钮。

一次订单可能收到重复回调，也可能真的出现额外到账；两者必须区分。相同渠道交易号只记一次；不同交易号的额外到账记录真实收款并进入多付处理，不静默丢弃，也不再授予重复权益。

### 状态分离

| 对象 | 状态／事实 | 不能混淆的边界 |
| --- | --- | --- |
| Order | 待支付、已支付、已关闭；购买快照保持稳定 | 关闭后若收到合法到账，仍按实际事实处理，不能直接丢弃资金事件 |
| PaymentAttempt | 待提交、处理中、结果未知、成功、明确失败／关闭 | 请求超时不是支付失败；同一未决尝试先查询再决定下一步 |
| PaymentReceipt | 已确认到账、可退款金额、已退金额 | 同事件去重；额外真实到账单独记录，不能用订单金额覆盖 |
| PurchaseGrant | 有效、已撤销；关联 orderId 与实际购买记录 | 授予存在不代表媒体当前可交付；进度和通知不是权益 |
| RefundApplication | 待审核、已撤回、已拒绝、已批准 | 用户撤回与审核竞争只能有一个条件更新成功 |
| RefundAttempt | 待提交、处理中／未知、成功、明确失败／关闭、异常待查 | 异常不等于终态失败；审批通过也不等于退款成功 |

前端分别展示“等待渠道确认”“已支付但内容暂不可用”“退款审核中”“已批准待提交”“渠道处理中”“需人工跟进”“已退款”。不得把支付／退款请求已受理当成完成，也不通过刷新页面重复发起资金请求。

### 首次可用与退款窗口

普通退款窗口由“合法购买已授予且课程可实际交付”的服务端事实起算，不使用用户首次播放或渠道原始付款时间。commerce 保存 `grantActivatedAt`、`firstAvailableAt` 及课程交付证据版本；firstAvailableAt 一旦可靠确定，不因重试、通知迟到或后续停供重置。

learning 保存内容可交付状态变更及有效时间。commerce 通过 `learningGetDeliveryEvidence` 获取自 grantActivatedAt 起首次进入可交付区间的证据；两项事实的交集确定首次实际可用。未交付或证据尚未取得时不虚构起点，保留未交付退款入口，并由恢复任务查询。

这里不把实时依赖查询失败解释为“从未可用”；未知与未交付分开。申请窗口以服务端收到申请时间判断，边界规则遵从 PRD；历史政策版本随订单保存，后续调整不能改写旧订单。

### 退款审核与渠道恢复

申请核对本人订单、到账与已退款事实。普通窗口内按 PRD 全额规则处理，不计算观看比例；超窗特殊原因仍可进入人工处理。运营队列覆盖待审、批准未提交、未知结果和超过目标时限的事项。

审批与撤回通过状态／版本条件更新；审批成功后建立唯一未决渠道尝试。发送失败或超时保留该尝试，使用相同业务退款编号查询原结果，不要求学员重新申请，也不直接创建新的退款请求。

渠道确认失败或关闭后才允许管理员发起关联重试；处理中、未知和“异常”都不满足重试新单的条件。回调和查询结果走同一处理函数，终态不能被迟到处理中通知回退；累计退款不能超过对应实际到账。

退款成功和撤销对应 PurchaseGrant 在同一 commerce 事务内完成。该退款只撤销它关联的购买授予，再按其他有效授予计算总访问资格；不能清空 userId＋courseId 下所有权益。

多扣款退款关联额外 PaymentReceipt；若该收款未产生合法购买授予，不撤销原购买。退款后回购产生新订单／新授予，旧退款迟到通知不能影响新购买。并发退款请求、回调与回购均需用实际持久化约束验证。

普通停售继续交付已购内容。必须撤回的课程由 learning 独立停止交付，同时进入通知及退款流程；停止交付不伪造“退款成功”，原路暂不可用也不能标成已到账。

## 4. HTTP 契约、数据与并发

公共路径前缀为 `/api/commerce/v1`；操作者从 identity 解析，学员不能传任意 userId 购买或退款。错误响应含稳定 code、message、requestId；前端依据错误类别提供查询或重试，不依据文案猜测资金终态。

| operationId／方法与路径 | 输入 → 输出 | 权限及主要错误 |
| --- | --- | --- |
| `commerceGetCoursePrice` GET `/courses/{id}/price` | courseId → 公开售价、币种、价格版本 | 仅已允许公开课程摘要；不是客户端指定金额接口 |
| `commerceSetCoursePrice` PUT `/courses/{id}/price` | 金额、币种、expectedVersion → 价格版本 | 管理员或有该课维护权讲师；learning 核验归属；冲突 409 |
| `commerceCreateOrder` POST `/orders` | courseId、idempotencyKey → orderId、金额／政策快照、状态 | 已验证账号；停止销售／已有权益 409；依赖失败 503 |
| `commerceCreatePaymentAttempt` POST `/orders/{id}/payment-attempts` | 支持渠道、idempotencyKey → attemptId、支付入口、状态 | 本人未支付订单；存在未决尝试返回原尝试，不重复扣款 |
| `commerceGetOrder` GET `/orders/{id}`；`commerceListOrders` GET `/me/orders` | ID 或分页 → 本人购买及支付摘要 | 本人或授权运营；不可读取他人订单；未知结果明确展示 |
| `commerceCreateRefund` POST `/orders/{id}/refunds` | reason、idempotencyKey → applicationId、状态 | 本人已到账订单；按政策处理；重复申请复用或冲突，不多退 |
| `commerceGetRefund` GET `/refunds/{id}`；`commerceCancelRefund` DELETE 同路径 | ID／expectedVersion → 退款状态 | 本人可读；只有待审核允许撤回，竞争失败 409 |
| `commerceReviewRefund` POST `/refunds/{id}/reviews` | decision、reason、expectedVersion → 审核／尝试状态 | 授权运营；不得把任意人工标记当渠道成功 |
| `commerceRetryRefund` POST `/refunds/{id}/retries` | 已确认失败尝试、expectedVersion → 新尝试状态 | 授权运营；存在未决结果时 409；保留原尝试链 |
| `commerceReceivePaymentEvent` POST `/providers/{provider}/payment-events` | 渠道原始通知 → 渠道确认响应 | 不用用户会话代替渠道验签；验签／金额不符拒绝并记录 |
| `commerceReceiveRefundEvent` POST `/providers/{provider}/refund-events` | 渠道原始通知 → 渠道确认响应 | 与查询结果共用事务处理；重复与乱序幂等 |

金额使用人民币最小单位整数或精确金额类型；价格和退款不使用浮点运算。交易记录不提供任意物理删除接口；运营查询需按职责与最小字段授权。真实渠道的通知响应协议在适配实现时核验，不能把本表当其官方签名说明。

### 内部契约与依赖方向

`commerceCheckEntitlement`：`POST /internal/commerce/v1/entitlements/check`，可信服务提供 `userId`、`courseId`、`purpose`，返回 `allowed`、`grantVersion`、`reason`。它只回答购买授予是否有效，不宣称课程可交付；learning 的 `learningCheckCourseAccess` 组合当前内容状态后才做最终访问决定。

下单调用 `learningGetSaleSnapshot`，维护价格调用 `learningCheckCourseManagement`，退款窗口查询 `learningGetDeliveryEvidence`；三者都不能反向调用权益检查形成递归。调用方验证服务身份、传播取消和 deadline；读取失败不凭过期价格／权限继续放行。

courseId、用户 ID 和版本由各拥有域提供，commerce 不导入其他服务业务包。免费课加入由 learning 记录学习关系；售价与免费／付费展示模式在发布契约中校验一致，免费模式不能创建伪支付事实。

事件通过本域待投递记录可靠重试。站内通知调用 community 的 `appendNotification(eventId, recipientId, type, target)`；接收方持久去重。发送课程和订单引用、必要金额／状态，不复制付费正文；投递失败不影响已提交的资金与权益事务。

### 数据权威与原子边界

| 数据 | 最小字段与约束 | 事务或恢复要求 |
| --- | --- | --- |
| Price／Order | courseId、价格版本；userId、课程及政策快照、币种、实付预期、幂等键 | 同账号幂等键唯一；金额取服务端；订单快照不随改价变化 |
| PaymentAttempt／Receipt | 业务尝试号、渠道请求／交易号、原始状态证据、确认金额 | 渠道交易号唯一；实际到账事实不得因订单先关闭被抛弃 |
| PurchaseGrant | grantId、orderId、purchase／payment 引用、userId、courseId、激活／撤销及版本 | 合法支付确认与授予同事务；对应退款成功与撤销同事务 |
| RefundApplication／Attempt | 原因、申请时间、政策版本、审核、对应收款／授予、尝试与未知状态 | 一个申请仅一笔未决尝试；按收款核验可退余额；审核撤回互斥 |
| AvailabilityEvidence | grantActivatedAt、firstAvailableAt、内容证据版本 | 首次可用只可靠确定一次；迟到事件不能缩短原窗口 |
| ChannelEvent／PendingDelivery | 事件去重键、处理结果；通知 eventId 与投递状态 | 渠道事件、权益更新及待投递事项一致落库；崩溃后可恢复 |

资源锁定或条件更新的具体 SQL 以实现为准，但必须在并发测试中证明：有效权益下阻止再购；同事件只生效一次；审核与撤回互斥；退款余额不透支。不能将 HTTP “先查再写”当成原子性保证。

## 5. 设计决定与取舍

| 决定 ID | 选择及依据 | 影响与限制 |
| --- | --- | --- |
| D-01 | 订单、到账与购买授予由 commerce 同域管理 | AC-04；本地事务闭合核心事实，不引入分布式事务框架 |
| D-02 | 申请、审批、渠道尝试与实际退款分开 | AC-15；允许追踪未知状态，避免自动重复退款 |
| D-03 | 每次购买对应独立授予；退款精确撤销 | AC-11、AC-15；覆盖重复扣款和退款后回购 |
| D-04 | 服务端可用事实＋订单政策快照 | AC-15；不以播放上报或查询到达时间缩短退款窗口 |
| D-05 | 可靠投递通知，资金终态不等消息送达 | AC-07、AC-12；首版使用本域持久化待投递，不默认消息中间件 |

## 6. 实施、发布与故障恢复

具体前后端任务与证据见[领域计划](../plan/005-交易退款与权益实施计划.md)。先完成订单、支付、权益与可信查询，再完成退款和异常恢复；接口约定后可并行开发页面，真实购买验收需身份与课程交付链路均成立。

上线前落实商户／渠道、回调可达与签名、支付和退款查询、交易号及幂等规则、渠道期限、人工处理责任与购买政策展示。单渠道先完成真实闭环；本文不默认选定微信、支付宝或 Stripe。

渠道中断时保留未知状态并查询原编号；查询也失败进入人工跟进，不自动重付或重退。巡检核对已付款未授予、重复到账、批准未提交、未知退款和通知未投递；运营可查看依据而不是直接改数据库。

数据库与渠道事实必须对账。回滚镜像不能撤销已经发生的收款、退款或合法授予；恢复备份后先核对事件和渠道，再幂等修复，不能简单重放所有外发资金请求。真实资金及生产恢复操作需后续明确授权。
