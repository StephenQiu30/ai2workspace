# 高质量 AI Workspace：文档、执行控制与交付验收设计

版本：1.1 · 日期：2026-11-15 · 状态：目标设计已确认；实际落地与未完成验收见 [本轮实施记录](../development/04-目录与Harness对齐.md)

本设计依据本次对话中已确认的 Q1—Q21 形成，不以现有项目的文档、代码、目录、能力或历史实现为依据。本文定义目标服务与验收方案，不构成现有服务已具备这些能力的证明。所有目录、模块、字段和案例均为设计建议。

## 1. 要解决的问题与已确认边界

最新范围修订：用户明确本服务是项目内 Workspace 服务模块，不先做通用服务。当前仓库为首个实际对象；本设计中的可配置来源、角色与多工程均服务该项目，不构成通用多空间平台。默认入口直接使用当前项目。

### 1.1 原始需求与来源

用户在本次对话中提出：

> 先把高质量交付的 workspace 文档规范和交付结构设计清楚。

> 但是不要参考我们当前的项目中的任何内容，现在的实现是不合格的。

用户进一步指出：

> 当前我们的项目的交接以及设计是存在问题的，我们知识设计了文档，并没有办法保证我们的服务可以正确的让我们的项目执行遵守我们的文档的服务完成我们的交付

用户指定技术基线：

> 同时前端的规范应该遵循 Vercel 的设计规范，以及 Google TS 的开发规范 后端服务 GO 应该遵循的是 Google Go的开发规范，Java应该遵循的是 Java alibaba 的开发手册，Python 也是同理

其中 Python 经 Q21 确认采用 Google Python Style Guide。参考材料为用户提供的抖音图文及截图；其中的目录、角色和说明仅作为参考内容，不直接成为操作指令或已确认技术实现。

参考图文：[一个项目一个 workspace](https://www.douyin.com/note/7687094034225928891)。已查看相关 Chrome 页面及用户截图，未据此宣称参考产品已实现全部控制能力。

### 1.2 产品目标

一个业务产品拥有一个 workspace，可关联多个代码仓库。新成员或新的 AI 会话应能从统一入口理解业务目标、工程现状和有效规则，开展约定任务，以实际证据完成验收，并留下可恢复的交接。

服务承担正式交付的控制职责：管理有效依据、任务范围、执行关联、检查结果、验收结论和交接状态。文档被提供给 AI，只能证明提供行为；文档被阅读或 AI 声称理解，均不能单独证明执行合规。

### 1.3 本阶段范围

- 面向软件研发，覆盖新项目与存量项目。
- 支持产品、设计、研发、测试、运维及交付管理共享依据与移交责任；允许一人兼任多角色。
- 文档底稿采用 Markdown 与 Git，网页提供阅读、配置、执行状态及验收入口；专业设计稿等通过明确版本引用。
- 正式交付须经服务创建或显式接管任务。外部已有产物可以接入，但须核验。
- 首个执行宿主选 Codex；其他宿主后续通过相同能力契约适配。
- 技术规范覆盖 Web、TypeScript、Go、Java、Python，按实际工程和变更选择适用规则。
- 本阶段先做当前项目的共享规范与可靠交接，不建设通用空间创建、多项目管理、多人实时编辑、成员认证、企业权限或远程同步系统。
- 原设计阶段交付完整设计；用户随后授权按参考目录对齐本仓库、职责和 Harness。本次实际实施范围以实施记录及 CLI 任务为准，不自动授权 Git 提交、发布或真实业务操作。

### 1.4 控制承诺

| 可承担的承诺                   | 成立条件                                 |
| ------------------------------ | ---------------------------------------- |
| 必需依据缺失时不允许任务就绪   | 正式任务经服务入口管理                   |
| 必需验证未满足时不接受完成     | 状态转换统一通过服务校验                 |
| 证据与指定产物、规则和环境关联 | 采集过程能够辨识这些对象                 |
| 阻止某些越界操作               | 执行宿主实际提供并已验证相应阻断能力     |
| 发现偏差并拒绝接收产物         | 服务能够观察变更、取得产物并执行对应检查 |

服务不承诺 AI 永远正确、所有自然语言要求均可自动验证，或服务范围外的操作一定会被阻止。目录约定、角色勾选、AGENTS 和 Skill 是协作入口；真实操作权限取决于已验证的执行能力。服务认可的完成状态也不自动等于代码已合并或服务已发布。

## 3. 文档与产物结构

### 3.1 建议逻辑目录

    workspace/
    ├── AGENTS.md                   Agent 入口和工作约定
    ├── .agents/skills/workspace-*/  各角色交付入口
    ├── code/                       工程关联说明、共享骨架、schema；本机配置不提交
    ├── harness/
    │   ├── README.md               服务约定、能力边界与操作入口
    │   ├── policy.json             必需检查与交付校验策略
    │   ├── roles.json              角色、目录职责和交付物
    │   ├── standards.md            技术规范及验证边界
    │   ├── templates/              需求、设计、验收、任务与空间样例
    │   └── tasks/                  共享计划和验收定义；运行状态由 TaskState 管理
    ├── src/content/                产品、架构、指南、开发与历史资料
    ├── public/media/               可公开图片和视频
    └── scripts/                    Workspace 自身的检查和初始化工具

这是内容归属，不要求每个任务创建全部目录或文件。文档展示站与具体目录布局可以调整，但唯一维护来源和稳定标识应保持可辨识。

服务另行保存规则包、任务约定、执行记录和证据索引。它们可以导出为文件，但网页和人工编辑的任务文档不能直接覆盖服务记录的检查事实及最终状态。

### 3.2 六类长期项目基线

| 内容           | 必须回答的问题                           | 维护责任           |
| -------------- | ---------------------------------------- | ------------------ |
| 项目概览       | 服务谁、解决什么、范围和当前阶段是什么   | 产品与业务负责人   |
| 产品与业务     | 关键术语、流程和有效业务规则是什么       | 产品               |
| 体验基线       | 操作、页面状态、视觉与组件遵循什么       | UI/UX              |
| 工程地图       | 仓库、职责、依赖、运行与检查入口是什么   | 技术负责人及研发   |
| 运行与发布     | 环境、配置类别、发布、观察和恢复如何完成 | 运维               |
| 协作与当前事项 | 角色、决策方式、任务、风险和交接在哪里   | 交付负责人及各角色 |

新项目尚未实现的部分写成目标、规划或待确认，不冒充工程现状。代码仓库内已有权威工程说明时采用版本引用，避免在空间里维护失去同步的副本。

### 3.3 每项需求的交付包

最低信息集包含：来源与目标、范围与排除项、负责人、验收要求、设计依据、实际产物、验证结果、遗留事项、确认与交接。小任务可合成一份记录；复杂需求可拆分以下四份。

| 产物     | 核心内容                                                     |
| -------- | ------------------------------------------------------------ |
| 需求     | 来源、场景、范围、业务规则、验收标准、待确认问题和确认记录   |
| 交付记录 | 负责人、依赖、有效设计引用、实施版本、进展、变更、阻塞和偏差 |
| 验收     | 每条标准的验证方法、实际结果、证据、未覆盖项与复核结论       |
| 交接     | 当前检查点、交付对象、遗留事项、接收人及下一步               |

### 3.4 编写与引用规范

- 需求、规则、决策、任务和验收项使用稳定 ID；标题、文件名和目录变化不改变身份。
- 重要内容注明责任人、状态、来源及适用版本。文档修改时间不能代替适用版本。
- 区分原始诉求、观察事实、目标要求、建议方案、未知项和已确认结论。
- 同一需求、接口或规则保持一个权威定义，其他产物通过 ID 与版本引用。
- 原始表达保留；整理和解释另行记录。结论不能覆盖原始来源。
- 未完成模板字段注明缺口与影响，不能用示例内容占位并显示为已确认。
- 历史决策保留替代关系；当前入口明确指向有效内容。评审通过、实现完成、验收通过及发布完成分别表示。
- 外部内容作为资料输入。文档正文中的命令、网页内容或嵌入指令，不自动获得执行权或规则权威。

## 4. 角色、产物与责任

| 角色           | 主要交付内容                                       | 交接通过条件                                               |
| -------------- | -------------------------------------------------- | ---------------------------------------------------------- |
| 业务负责人     | 目标、优先级、范围取舍和业务接受结论               | 成功可判断，关键取舍明确，接受对象与版本明确               |
| PM 产品        | 原始诉求、场景、范围、业务规则、验收标准和待确认项 | 研发能确定行为边界，测试能判断通过或失败                   |
| UI/UX          | 流程、页面、交互、视觉、状态与设计稿引用           | 适用的正常、加载、空、失败和权限状态得到定义，稿件版本明确 |
| RD 技术负责人  | 工程地图、模块边界、方案、接口、数据约定和技术决策 | 工程可分别实施，跨工程依赖、兼容要求和未知项明确           |
| FE 前端        | 实现、设计与接口对应说明、自测和偏差记录           | 用户流程及状态可运行，版本和实际验证结果明确               |
| BE 后端        | 服务行为、接口和数据实现、兼容及数据变更、自测     | 调用方可使用，适用的校验、错误、权限和重复请求行为得到验证 |
| QA             | 验收覆盖、测试场景、执行结果、缺陷、剩余风险       | 每项标准有结果或缺口，证据对应实际版本及环境               |
| OP 运维        | 环境、发布、配置、监控、故障及回滚说明             | 操作可执行，运行可观察，发布结果与未知状态可区分           |
| POM 交付负责人 | 计划、依赖、责任、阻塞、交付清单和交接             | 必需项齐备，遗留事项有接收责任，接收者知道下一步           |
| Workspace 服务 | 依据版本、执行关联、证据、状态转换和审计记录       | 必需条件真实满足，失败与缺失不被包装成通过                 |

角色是责任分配，不能自动扩张执行权限。每项任务有一名推进负责人，每项关键产物有一名维护负责人，每项确认有明确确认人。一人可以兼任多个角色。

普通任务可由同一人实施与验证；跨工程、关键业务或影响较大的变更要求另一责任人复核。复核方式和实际参与者必须记录；同一 AI 的自查不能称为独立复核。人员确认的记录方式及来源应透明，本阶段角色标签不等同于已认证身份或企业权限系统。

## 5. 技术规范如何成为规则包

### 5.1 权威来源与适用边界

| 规则包             | 来源                                                | 自动检查候选                                       | 仍需专业判断的内容                             |
| ------------------ | --------------------------------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| Web 界面           | Vercel Web Interface Guidelines                     | 语义和标签检查、可访问性扫描、浏览器流程及布局验证 | 焦点清晰度、状态表达、反馈、恢复路径与实际体验 |
| React/Next.js 专项 | Vercel React Best Practices，仅用于采用该框架的工程 | 框架 lint、构建、性能测量与专项检查                | 组件边界、数据获取及性能取舍                   |
| TypeScript         | Google TypeScript Style Guide                       | 选定配置的 formatter、ESLint 或 gts，以及类型检查  | 命名、类型模型、注释质量及断言理由             |
| Go                 | Google Go Style Guide 及采用的配套规范              | gofmt、go vet、编译与测试                          | 清晰性、抽象、命名、错误处理与接口设计         |
| Java               | Alibaba Java 开发手册                               | 验证兼容的 P3C-PMD 规则、编译与测试                | 设计、业务语义、并发与数据访问方案             |
| Python             | Google Python Style Guide                           | 采用固定配置的 Pylint、选定 formatter，以及测试    | 类型与模块设计、异常语义、命名和注释           |

自动检查候选不等于已安装、已兼容或已运行。规则包启用前必须在隔离样例中验证工具、配置、输入范围和结果判定。不能仅运行默认 PMD 就声称检查了 Alibaba 规则，也不能用类型检查代替风格规范。

Vercel 界面规范作为交互与界面质量基线；项目视觉、品牌、组件及页面规则另行定义。采用 Vercel 的规范不自动要求部署到 Vercel，亦不自动要求使用某个组件库。

保留原规范的层级。Google Go 的 Guide、Decisions 和 Best Practices 有不同地位；建议内容不能无记录地升级为强制要求。外部规范与项目要求发生冲突时，由相应责任人确认采用关系和差异；执行者不能自行选择更宽松的一方。

### 5.2 规则登记

每条被采用的重要要求至少保存：

| 字段             | 含义                                                  |
| ---------------- | ----------------------------------------------------- |
| ruleId、revision | 本地稳定 ID 与不可变修订                              |
| source           | 官方地址、章节、固定版次或 commit、内容摘要及访问日期 |
| appliesTo        | 语言、工程、文件、用户场景及适用前提                  |
| obligation       | 必需、建议或经确认不适用；保留来源要求层级            |
| mechanism        | 执行前约束、自动检查、专业复核或业务验收              |
| verification     | 检查定义或人工验收清单，以及明确通过条件              |
| evidenceRequired | 所需产物、运行、观察或确认记录                        |
| owner、reviewer  | 维护和复核责任                                        |
| exceptions       | 已确认差异、范围、理由、责任人及处理安排              |

不适用必须有适用性判断。需要判断但缺少结论的条目保留为待确认，不能自动当作不适用。

### 5.3 版本、升级与工具配置

同时固定规范、工具及配置版本，并记录编译器或运行时。在线链接用于追溯；进行中任务使用已固定的内容，不随网页更新漂移。具体 commit、手册版次与工具组合在实现准备时确定，本文不冒充已完成版本固定。

规范升级作为独立变更：比较差异，确认适用性，验证工具覆盖，评估存量影响，经责任人确认后生效。进行中任务继续使用原依据，或通过有记录的任务修订采用新依据，并重验受影响结果。

检查步骤默认只读。格式修复、自动重构、配置生成和依赖安装属于修改步骤，明确记录其结果，再检查最终产物。例如 gofmt 的列表结果要判空，不能只看退出码；格式化写入后的代码需要重新验证。

### 5.4 存量工程与例外

首次接入记录完整检查结果和已有违规基线，再要求新增及修改内容遵守规范，同时运行任务所需的整体回归。历史债务不能成为跳过全部检查的理由。

违规身份不能只依赖容易移动的行号，至少结合规则、文件、位置上下文和内容特征；无法可靠区分新旧时要求复核。删除旧问题不能抵消新增问题，规则配置变化也不能伪装成违规减少。

差异可由有责任的人显式接受，记录精确范围、原因、版本和后续安排；必要时设到期条件。检查事实仍保留为失败或违规，验收结论显示“存在已接受差异”。缺失证据、未知结果、未授权操作及无法确认的产物身份，不能被改写为检查通过；需要的范围变更应走任务修订。

## 6. 服务架构与核心记录

以下是逻辑模块，可由一个服务进程实现；本设计不要求拆分微服务。

| 模块           | 责任                                             |
| -------------- | ------------------------------------------------ |
| 空间与工程登记 | 业务项目身份、来源、仓库职责、共享关联与本机绑定 |
| 文档与规则管理 | 内容身份、版本、引用关系、适用性及规则包         |
| 任务准备       | 形成可执行约定，固定依据，检查准备条件           |
| 执行适配       | 对接 Codex，声明真实能力，关联运行和产物         |
| 检查与证据采集 | 运行获准检查，采集原始结果，管理有效性           |
| 验收与状态判定 | 计算缺口，处理人工确认及例外，控制转换           |
| 交接与恢复     | 保存检查点，比较现场，识别可复用与失效结果       |
| 事件与导出     | 记录关键变化，提供可审阅的交付包和来源           |

核心记录包括：

- 项目与工程：业务身份、工程标识、仓库来源、职责、工程依赖；本机目录与个人配置另存。
- 规范与规则：来源、固定修订、适用范围、验证方式及已确认差异。
- 任务约定：需求依据、目标、排除项、输入、输出、工程范围、适用规则、检查、验收、责任和交付条件。
- 执行记录：任务修订、宿主能力、运行标识、开始结束、观察、产物与中断情况。
- 产物集合：每个工程的提交和实际内容身份，含必要的未提交及未跟踪文件状态，以及文档、设计稿和其他产物版本。
- 检查定义与运行：工具、配置、输入范围、通过条件、环境、原始输出及结果。
- 验收与例外：逐项结论、证据引用、复核来源、确认对象及差异。
- 交接检查点：约定修订、依据、产物、有效证据、未知外部动作、接收责任及下一步。

已有记录修订时保留前后关系。关键写入校验预期修订，避免并行覆盖；状态变化与对应事件一同可靠保存。执行请求具有幂等标识，重复请求不会无记录地创建第二次执行。运行中进程和外部操作另行核实，不能只依赖请求去重。

## 7. 任务准备与执行控制

### 7.1 可执行任务约定

在执行前形成并确认以下内容：

1. 解决的问题、需求 ID、可观察目标及排除项。
2. 有效需求、设计、规则和工程基线的固定引用。
3. 目标工程、允许修改的路径和预期交付产物。
4. 起始现场，包括已有修改及其归属；保持已有内容，不能静默清理。
5. 任务适用的规则、自动检查、人工复核和业务验收要求。
6. 推进、实施、复核、业务确认与接收责任。
7. 执行宿主能力及相应控制边界。
8. 任务已获授权的操作范围，以及需要另行确认的外部动作。
9. 完成条件，包括是否要求交接、合并、发布及其证据。

文档维护任务也使用相同原则，但只选择与其相适用的检查，不能机械要求运行所有语言和业务服务。

### 7.2 准备通过条件

服务必须能够确定：依据可访问且身份明确；关键结论不冲突；工程可辨识；输出范围明确；适用规则已确认；必需检查有可用执行方式；责任与完成条件明确。

准备过程可发现问题并提出补齐建议。AI 可以提议规则映射与任务约定，但未经确认的推断不能自动成为新强制规则。只阻止依赖缺失依据的工作，允许不依赖该缺口的调查或准备继续开展。

已开始的外部任务必须显式接管，记录接管时刻、已发生变化、可验证事实和未知事项，不能补造执行前现场。

### 7.3 Codex 适配能力契约

| 能力           | 必须提供的结果或声明                                   |
| -------------- | ------------------------------------------------------ |
| 上下文提供     | 本次提供的依据、版本、规则、目标和限制清单             |
| 会话与运行关联 | 能辨认任务对应的实际运行及其生命周期                   |
| 操作控制       | 逐项说明可阻断、可观察或不支持的操作                   |
| 产物观察       | 能取得并辨认实际变更与交付内容                         |
| 中断处理       | 区分已结束、仍运行、中断和结果未知                     |
| 恢复处理       | 基于检查点与当前现场继续，而非假装恢复不存在的宿主状态 |

具体接入方式必须先做实际能力验证。本设计不预设 Codex 存在某个未核验的 API、hook、会话读取或路径沙箱能力。某能力缺失时，应降低相应控制声明，或将依赖它的任务标为未准备完成；不能用提示词伪装成权限控制。

初期正式交付控制集中在任务准入、产物接收和完成判定。宿主实际支持并通过验证的阻断能力再用于执行前控制；其余由观察、检查及拒绝交付承担。

### 7.4 执行中变更与范围控制

任务输入作为资料传递，执行命令来自已确认的检查或操作定义。不能从任意文档正文自动提取命令并执行。

任务范围、规则、验收或关键依据变化时，创建新修订，记录原因和影响，再决定是否重建执行基线。执行者不能直接删除必需检查、降低通过条件或修改事实记录以获得完成。

执行中发现越界时，按已验证能力中断相关操作，保留现场与事件，并阻止接收不合格结果。涉及原有或并行修改时，不自动回滚、覆盖、清理或提交；先确定归属和授权。

### 7.5 状态与条件

任务阶段建议采用：待准备 → 可执行 → 执行中 → 待验证 → 待验收 → 待交接 → 完成；不需要单独交接的简单任务可在约定中合并交接记录。

阶段之外分别记录当前条件：正常、缺少依据、能力不足、执行中断、检查失败、证据过期、存在冲突、等待确认。这样“待验证”任务能够同时表达“上次检查失败”，不丢失失败事实。

只有服务按最新任务修订计算通过条件，才可推进到完成。执行者的完成消息和人工直接编辑状态字段，只能视为申请或输入。完成后的产物若变化，应显示原完成结论对应的历史版本，后续变更开启新任务或明确修订，不能把旧结果当作当前验证。

## 8. 检查、证据与失效管理

### 8.1 三类证据

| 类别         | 来源                             | 可证明什么                                   |
| ------------ | -------------------------------- | -------------------------------------------- |
| 自动执行证据 | 服务按固定检查定义实际运行并采集 | 该输入、版本和环境下的检查结果               |
| 人工验收证据 | 具体责任人对指定对象作出确认     | 该人的观察、判断与接受结论                   |
| 外部导入证据 | CI、报告或外部验证记录           | 经核验后支持的特定结论；来源未核验时保留限制 |

AI 说明、截图和测试报告都需要核对证明范围。截图可支持可见状态，不能单独证明全部交互或后端效果。AI 评审可作为辅助分析，标明模型评审来源，不冒充业务负责人确认或独立人员复核。

### 8.2 检查定义与结果

检查定义保存稳定 ID、版本、适用范围、执行工具、配置、输入、环境、超时、通过条件、输出解析和必需程度。输出解析同样需要验证，不能将缺失报告解释为空问题。

检查运行绑定任务修订、产物集合、规则包、工具配置及环境，保存开始结束、退出码、原始输出或可访问引用、报告与解析结果。运行失败、工具异常、未运行、不适用和证据过期分别表示。

检查入口和事实写入由服务管理。执行者可以请求运行或提出配置修改，但不能通过自报结果创建服务采集证据。输出内容来自被检查工程时仍需审慎解释；原始输出可追溯不等于结果永远可信。

### 8.3 有效性与重验

- 代码、文档或设计产物变化后，比较实际检查输入，识别受影响证据。
- 规范、检查器、配置、工具链或关键环境变化后，重新判断证据有效性。
- 精确依赖关系已验证时，可仅重验受影响检查；无法证明无关时重验相关必需检查。
- 无关内容变化不必使所有证据失效，但不能仅依靠文件扩展名判定无影响。
- 人工确认也绑定产物和验收版本；实质变化后重新确认。
- 外部报告若无法对应产物、环境或运行来源，保留为参考，不满足必需自动证据条件。
- 原始证据保留，失效只改变可用于当前验收的资格，不能删除失败历史。

## 9. 验收、例外和完成判定

### 9.1 每条验收标准

至少包含：ID、前置条件、触发动作、可观察结果、验证方法、责任人和证据要求。避免“体验良好”“按规范开发”“功能正常”等无法判断的单独表述。

服务呈现完整对应关系：需求 → 验收标准 → 适用规则 → 检查或复核 → 产物与证据 → 结论 → 确认人。

### 9.2 完成条件

1. 使用最新且已确认的任务约定，依据与产物身份明确。
2. 预期产物齐备，实际改动范围已核对，未知归属得到处理。
3. 每项必需验收有有效证据；缺失、失败、过期及不适用明确区分。
4. 必需专业复核及业务确认齐备，例外有对应责任人的明确接受。
5. 项目基线影响已检查；需要的更新与本次交付一起完成，不涉及更新时留下简要结论。
6. 遗留事项有责任人与处理安排，交接内容满足接收条件。
7. 如果任务明确包括合并或发布，取得相应实际结果；没有授权不能为完成而自行操作。

允许的结论包括：通过、存在已接受差异、未通过、证据不足。服务界面必须显示这些区别。存在差异的接受不是把检查失败改写成通过。

代码风格、构建、测试、浏览器体验、业务接受及发布观察是不同维度。各维度按任务适用性要求，不由其中一项替代全部。

### 9.3 界面设计

服务入口围绕用户决定组织：项目现状、需求与依据、任务准备、执行进展、检查结果、验收及交接。显示可执行的下一步和具体缺口，例如“缺少键盘流程验收”或“产物变化，需要重新验证”。

技术字段用于展开的证据详情；主要页面使用业务名称。规则来源、版本、检查原文和历史事件可追溯，但不要求用户先理解内部数据结构才能完成工作。

## 10. 交接、跨会话恢复与并行协作

### 10.1 交接检查点

保存目标、有效约定、需求和规则修订、工程与文档现场、运行状态、产物、证据、决策、未完成事项、阻塞、接收责任和下一步。原始会话历史可以作为补充，但不能成为理解交接所必需的唯一依据。

对每个重要外部动作注明未开始、已观察完成、已观察失败、仍在运行或结果未知，并保留可核验的外部标识。请求发送成功不能直接代表业务操作成功。

### 10.2 恢复步骤

1. 读取检查点与对应依据，而非只显示导出路径。
2. 核对工程位置、版本、工作区变化和运行状态。
3. 比较任务约定、规则及检查配置，识别漂移。
4. 列出可复用证据、失效证据、冲突和未知事项。
5. 核实结果未知的外部操作，再决定继续、重验或请求确认。
6. 为新的执行关联记录来源，保留前后检查点关系。

跨会话恢复指新会话凭服务记录继续工作，不要求宿主能够原地恢复内存或原会话。不能自动重放未知的发布、提交、数据操作或重复启动仍在运行的工作。

### 10.3 并行协作

每项任务保存起始依据和预期修订，写入时比较当前版本。任务可以并行研究不同内容；冲突范围需要明确，不能仅凭角色目录互不相同就判断没有业务冲突。

同一需求、规则、接口或共享产物变化时，通知依赖任务并要求影响判断。服务防止自身记录静默覆盖；工程文件的合并仍需实际工具支持和明确处理。未完成的并行修改保留，不自动清理。

## 11. 新项目与存量项目接入

| 场景     | 最小准备内容                                                                 | 首次交付验证                                   |
| -------- | ---------------------------------------------------------------------------- | ---------------------------------------------- |
| 新项目   | 业务目标、范围、角色、体验及技术初始决策、工程计划、验收要求                 | 从已确认需求完成一个范围受控的真实任务         |
| 存量项目 | 实际工程地图、运行和检查方式、关键业务流程、现有约束、违规基线、问题及未知项 | 新成员或新 AI 能定位真实工程并完成一个受控改动 |

先建立足够支持首个任务的基线，围绕实际使用逐步补齐。不能要求先补完所有历史文档才能开展任何工作，也不能把未经核验的 AI 工程总结当作事实。

接入报告区分已观察、资料声称、推断和未知。缺少私有环境或实际运行条件时，准确描述能证明的范围；该缺口若影响必需验收，保留为未完成条件。

## 12. 分层验收方案

### 12.1 三层对象

| 层级        | 验收对象                         | 核心问题                             |
| ----------- | -------------------------------- | ------------------------------------ |
| A：服务机制 | 规则、执行、证据、状态及恢复实现 | 不合格结果能否被正确识别和拒绝       |
| B：空间交付 | 一个实际 workspace 的资料与规则  | 陌生接手者能否找到可信依据并开展工作 |
| C：项目任务 | 某项真实需求的实际结果           | 约定目标是否满足，交接是否可用       |

模拟适配器用于确定性失败和中断测试；真实 Codex 用于验证实际执行关联；实际新会话用于验证接续。三者分别记录，不互相冒充。

### 12.2 服务与真实交付验收矩阵

| ID    | 操作或故障注入                                      | 必须观察到的结果                                     | 必需证据                           |
| ----- | --------------------------------------------------- | ---------------------------------------------------- | ---------------------------------- |
| AC-01 | 一个业务项目关联前后端两个工程                      | 身份、职责及本机位置明确，任务能选择适用工程         | 共享登记、本机绑定与任务记录       |
| AC-02 | 输入原话、参考资料、AI 推断及确认                   | 分类与来源可辨识，推断不自动成为规则                 | 原始内容、整理内容及确认记录       |
| AC-03 | 分别准备小任务与跨工程任务                          | 必需信息完整，专项产物按适用性增加                   | 两类交付包及适用性判断             |
| AC-04 | 为 TS、Go、Java、Python 配置合规及违规样例          | 对应规则能发现预期问题，覆盖缺口明确                 | 固定规则、工具配置、样例及原始运行 |
| AC-05 | 缺少关键需求、冲突设计或无法访问工程时请求执行      | 相关工作不能就绪，具体缺口可见                       | 请求、阻断事件和页面观察           |
| AC-06 | 用真实 Codex 执行一个受控任务                       | 上下文、运行、产物和宿主能力实际关联                 | 真实运行、能力验证及产物差异       |
| AC-07 | 执行者填写“测试通过”但未运行检查                    | 不能满足必需检查，也不能完成                         | 自述、服务证据列表及拒绝结果       |
| AC-08 | 检查失败、工具缺失、超时、报告缺失或 gofmt 输出非空 | 分别正确分类，均不能误报通过                         | 原始输出、解析结果和验收缺口       |
| AC-09 | 检查后改变代码、设计、规则或工具配置                | 受影响证据失去当前验收资格，要求重验                 | 前后内容身份及重验决策             |
| AC-10 | 导入错误产物版本或来源不可核验的外部报告            | 标明来源限制，不满足对应必需证据                     | 报告元数据、核验和拒绝结果         |
| AC-11 | 执行者删除必需检查或降低标准后申请完成              | 识别约定变化，不能直接完成                           | 修订差异、确认缺口与状态事件       |
| AC-12 | 已有违规基线上新增、移动、删除问题                  | 新增不被历史债务抵消，难以辨认时复核，整体回归仍执行 | 基线、差异、全量结果及复核         |
| AC-13 | 责任人接受一个指定差异                              | 保留原违规，显示已接受差异及范围，不伪造通过         | 失败结果、例外和最终结论           |
| AC-14 | 高影响任务缺少独立复核或业务确认                    | 阻止完成，补齐后才可接受                             | 角色要求、复核来源和业务确认       |
| AC-15 | 并行任务修改同一接口、需求或共享产物                | 检出冲突，不静默覆盖，依赖任务得到影响判断           | 前后修订、冲突事件和处理记录       |
| AC-16 | 中断执行、重复发起、外部动作结果未知                | 不误报成功，不无记录重复执行，保留现场并先核实       | 运行标识、中断记录和恢复观察       |
| AC-17 | 多工程只完成其中一个后申请完成                      | 显示未满足工程及产物，不能完成                       | 多工程产物清单和逐项结果           |
| AC-18 | 无历史聊天的接手者从空间入口开始真实任务            | 能找到有效需求、设计、工程和规则，完成约定任务       | 接手过程、缺口、产物及验收         |
| AC-19 | 完成后需要更新工程或业务基线                        | 更新与交付关联；未更新时不能满足必需交付条件         | 基线影响检查与更新差异             |
| AC-20 | 实际新的 Codex 会话接续一个中断任务                 | 实际读取依据，识别漂移，复用有效证据并完成余项       | 两个真实会话的执行与交接记录       |
| AC-21 | 任务只要求实现验收，或另行要求发布                  | 分别判断，不误报合并和发布；要求发布时核验实际结果   | 完成约定、验收及必要的外部记录     |
| AC-22 | 浏览器验收任务准备、失败恢复、验收和交接页面        | 键盘、焦点、表单反馈及状态可用，缺口能指向下一步     | 浏览器交互记录、观察和问题关闭结果 |

AC-04 按当前项目实际绑定工程启用规则。当前 TypeScript 先实际验证；未来绑定 Go、Java、Python 工程时分别验证对应工具组合，不能以 TypeScript 通过代表其他语言支持。Web 界面规则的静态检查覆盖由 AC-04 的扩展样例验证，实际体验由 AC-22 及任务专项验收验证。

AC-06、AC-18、AC-20 和 AC-22 必须保留真实验证记录。同一会话摘要、测试替身、单独命令进程或仅打开网页，不能替代相应实际验收。

### 12.3 实际验收执行顺序

1. 固定验收候选：设计修订、规则包、工具链、服务版本和样例工程版本。
2. 运行当前项目适用规则包的正反样例，证明工具配置、通过条件和缺口表达有效。
3. 验证任务准入、越界检测、证据有效性、例外、并发和中断等机制。
4. 在真实 Codex 中开展至少一个完整任务，并完成实际浏览器交互验收。
5. 在新项目与存量项目两类试点中验证接入，整体覆盖一个多工程交付。
6. 实际新 Codex 会话接续中断任务，完成现场核对、重验和交接。
7. 汇总逐项结果、缺陷、剩余差异及其接受责任，形成最终验收结论。

上述试点可复用受控样例工程。实际业务环境仅在任务范围和授权明确后采用。测试替身证据与真实宿主证据分别列出。

### 12.4 验收结论与交付包

最终交付包应包含：需求与设计版本、规则来源及覆盖映射、宿主能力报告、样例和候选身份、自动检查记录、浏览器观察、专业复核、业务确认、例外、已知缺口及接续记录。

必需机制、真实宿主或跨会话验收未完成时，结论写明未完成及阻塞，不标记正式验收通过。允许的差异经责任人接受后以“存在已接受差异”呈现，仍需满足不可缺失的证据身份与实际执行要求。
