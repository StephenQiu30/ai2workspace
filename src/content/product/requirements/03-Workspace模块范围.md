# 项目 Workspace 模块范围

需求 ID：REQ-WS-MODULE。来源：本次用户对话，2026-11-15。状态：用户已确认定位；实现与验收事实由实际任务及实施记录提供。

## 原始要求

> 我文件的设计目录按照这个规范来，职责清晰，以及对应的harness服务，来确保我们的整个计划的实现和我们的当前仓库的规范是完全一致的，不需要反复作出转正

用户随后进一步明确：

> 当前我们做成了一个通用的体系，但是我们当前的服务他应该是作为一个workspace服务模块存在，不要先做通用服务

本结论优先于先前通用知识治理、多空间平台定位。保留原始需求和实现历史，不将历史确认为当前产品范围。

## 范围

服务是项目内的 Workspace 模块：一个项目的文档、角色、代码工程关联、规则、任务和交接共同服务该项目的交付。当前仓库是第一个实际使用者。默认直接进入当前项目，不以空间广场、创建通用空间或跨项目管理作为首期流程。

根 AGENTS 与角色 Skill 负责进入；code 说明工程关联；harness 负责角色、检查和交付判定；src/content 保存项目资料；public/media 保存可公开媒体；scripts 保存项目自身工具。工具本身的 apps 与 packages 保留工程职责，不复制到业务代码引用目录。

## 本轮验收

- 文件按上述职责归属，正文不在 docs 和 src/content 中双重维护；旧文档 ID 和历史快照保留。
- 默认网页、配置和指南围绕当前项目 Workspace；通用空间创建入口不作为产品流程。
- 根规范、角色、Skill、共享合同与实际必需检查可由一致性检查核对。
- Harness 拒绝遗漏必需检查、无效角色、越出角色职责的声明以及越出精确输出的实际变更。
- 策略变化使旧依据过期，显式重建不能洗掉原始未授权范围差异。
- 真实检查与交互回归通过；尚未实现的 Codex 执行控制和完整验收不得虚报完成。

## 边界

本轮不重建通用平台，不新增多租户、成员权限、跨机同步、通用工作流引擎、其他宿主抽象层或多语言工程示例。现有底层兼容类型和历史读取可保留，不能据此宣称未来产品能力已完成。
